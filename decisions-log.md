# Care Log — Decisions Log

A running record of structural and product decisions, so future work builds on what's already
been decided rather than re-deriving it. "Open questions" are things flagged but not yet settled.

---

## Decided

| Area | Decision |
|---|---|
| Storage | Local-only by default; local DB encrypted at rest, key derived from a user passcode (PBKDF2 + AES-GCM), never stored in plaintext |
| Free tier | 3 active symptom trackers, 15 distinct medications, on-device text report, manual encrypted backup/export — all free, no account required |
| Paid tier & pricing model | Physician sharing is subscription. Cloud sync pricing hinges on manual vs. automatic, not on destination: manual "back up now" stays free always, to any destination (including a user-supplied cloud location), consistent with the original free-tier backup decision — zero ongoing cost regardless of where it points. Automatic/background sync is the actual paid feature, at two price points: full price to Claude's managed infrastructure (real hosting cost), cheaper for automatic sync to a self-supplied location (no hosting cost, but real ongoing engineering/maintenance cost to build and keep provider integrations working). A 3rd+ profile is a one-time purchase, not a subscription — pure local capability unlock with no ongoing cost to serve. First two profiles are free, specifically to cover the sick-single-parent-tracking-themselves-and-their-child scenario without requiring payment at the exact moment someone may least be able to act on that. General rule: one-time price fits features with no ongoing cost; subscription fits features with real recurring cost, whether that cost is hosting or maintenance |
| Backup/sync tiers, clarified | Three distinct things, not two: (1) manual export/backup to any user-chosen location via the OS file picker — always free, unchanged from the original free-tier decision, zero cloud-provider integration needed; (2) automatic/background sync to a user-supplied location (their own Dropbox/Drive/self-hosted server) — paid subscription, cheaper tier, since no storage cost is borne by the business, though it still requires real integration engineering (Dropbox/Drive APIs or a protocol like WebDAV) — same complexity as managed sync, just not the storage cost; (3) automatic/background sync to Care Log's own managed servers — paid subscription, full price, real ongoing storage cost. All real integration complexity stays confined to the two paid tiers; the free tier remains exactly as simple as already built |
| Physician sharing | Recipient never pays, logs in, or creates an account — access via unauthenticated, expiring, revocable token |
| Cloud data retention | Never auto-deleted; only removed on explicit user request, and that deletion must reach backups/logs too, not just the primary record |
| Backup/export | Manual-trigger only, encrypted with the same passcode as the app, via OS file picker/share sheet |
| Marketing/monetization | No dark patterns, no pop-ups ever, no data selling, no sponsorship (including "sponsor-reviewed" content); usability wins over growth/revenue by default |
| Distribution | PWA-based core + thin native wrappers (Tauri/Capacitor); billing must be channel-specific (Apple IAP, Play Billing, direct web for F-Droid/GrapheneOS/Sailfish) |
| Enterprise | InstitutionalLicense model for health systems and individual practices — same mechanism, self-serve for small practices vs. sales-assisted for large systems; needs a periodic online validity check with ~30-day offline grace period |
| Physician trial codes | Reusable per-physician code, 14-day free trial, no account or payment info required to redeem |
| Templates | Never filtered by demographics — full illness-template list always shown regardless of age/sex/gender |
| Demographics | Age (required) and ethnic background (optional) collected at setup; name/sex/gender (all optional) deferred until report export/share |
| Range tailoring | Age-based tailoring is safe to build (well-supported pediatric/adult thresholds); ethnicity-based tailoring requires individual clinical justification, not a blanket feature |
| Units | Canonical storage in one internal unit per category, converted at display/input boundaries; separate toggles for metric/imperial and glucose (mg/dL vs mmol/L); blood pressure always mmHg, no toggle |
| UI | No animations/transitions anywhere; optimize for fastest load; fewest taps by default; large type, WCAG 2.1 AA floor, full screen reader support, no color-only indicators |
| First-run UX | Nothing but a single "Track a symptom" button until any data exists |
| Writing boundary | Claude never writes final prose meant to read as the user's voice (marketing copy, origin story, etc.) — outlines and brainstorming only |
| Fact-checking | All medical/accessibility/security claims verified against multiple current, authoritative sources — disagreements flagged, not silently resolved |
| Standalone build | `care-log-standalone.html` is generated from `care-log-prototype.jsx` via a scripted transformation (imports stripped, `window.storage` → real `localStorage`-backed `LocalStore`, lucide-react → inline SVG icons), regenerated after every source change rather than hand-edited separately, specifically to prevent the two files drifting apart |
| PWA dependencies | CDN dependencies (React, ReactDOM, Babel Standalone) must be version-pinned to a major version (e.g. `@7`, `@18`), never left unpinned — an unpinned Babel silently jumped to a breaking major version (v8's JSX runtime default change) and caused a fully blank page with no error |
| Service worker caching | Network-first with cache fallback, not cache-first — cache-first was silently serving stale content and required two reloads to show any update, a bad fit for an actively-developed app; cache name gets bumped on every meaningful change to force a clean slate |
| Chart time domain | All tracker charts and medication markers share one synchronized timeline (not independently computed per chart), adjustable via pinch/drag gesture or 24h/3d/7d/All preset buttons, clamped to the real logged data range with a minimum zoom span |
| Medication chart display | No on-chart text labels for medications (repeated overlap/cutoff/hard-to-read problems with diagonal text) — markers are diamonds in a dedicated row below the plot, full detail lives in a tap-to-expand "Medications in view" list scoped to the chart's current visible range |
| Temperature value labels | Bounded, not all-or-nothing: label every point when ≤8 are visible, otherwise always show exactly "Now" and "Peak" (never fully unlabeled, never cluttered) at any zoom level |
| Data editing | Both symptom entries and medications are fully editable (value/name/dose and timestamp) and deletable after logging, not just deletable |
| Logging discipline | Claude adds a row to `ai-usage-log.md` and `decisions-log.md` immediately within the same turn as any substantive change, not deferred to a later "catch-up" — see note at the bottom of this file |
| Health concern grouping | Trackers can belong to multiple health concerns at once (many-to-many, not one tracker = one group) — a symptom like cough can legitimately sit under both "Cold/Flu" and "Allergies". Concerns are created/selected during the template-add flow (reuses an existing concern by matching name rather than creating duplicates); dashboard has an "All / By health concern" toggle with an "Other" section for untagged trackers |
| Questionnaire tracker type | New tracker type for score-based clinical instruments (PHQ-9, GAD-7, user's modified Goldberg depression scale), distinct from temperature/scale/boolean — stores raw per-question responses plus computed score/band, not just a single value. Counts as one free-tier tracker slot regardless of internal question count. Lives in a separate "Mental health" section of the template picker, not mixed with fast single-tap symptom templates, since the interaction model (multi-question form) is genuinely different |
| Questionnaire licensing | Every QuestionnaireDefinition must carry an explicit `licenseStatus` field (public-domain / used-with-permission / original-work / needs-review) — instruments at "needs-review" don't ship until resolved. PHQ-9 and GAD-7 verified public domain (Pfizer explicit release). User's modified Goldberg Depression Scale is "needs-review": the original is explicitly copyrighted ("All rights reserved," one source restricts to personal use), and a modified version may still count as a derivative work requiring permission — not resolved, Claude is not positioned to make the final call |
| Questionnaire safety items | Any question can be flagged `isSafetyCritical` (e.g. PHQ-9 item 9, self-harm ideation) for documentation purposes only. Resolved: Care Log is symptom-tracking software, not a crisis service, and never claims or attempts to be one — a concerning answer is logged like any other data point, with no detection, no reactive response, and no interruption. This is a firm product boundary, not a per-instrument decision. Open, user's call: whether a single always-present, non-reactive support-resources entry (e.g. in Settings) is worth including, as a distinct question from intervention |
| Custom trackers (built) | Adding "Track a symptom" needs a path for anything not covered by the six official templates — discoverable both via a plain "Add a custom symptom" option in browse, and by offering it as the natural next step when a search comes up empty (pre-filled with what was typed). Custom tracker creation: name + a plain type choice (Rate severity 0-5 / Yes-No / Number, defaulting to severity) + the existing health-concern step. A new "Number" type is distinct from "Temperature" — general numeric trackers shouldn't inherit fever-specific shading/unit conversion; auto-scales its chart range to actual logged data rather than a fixed range. Blood pressure and other paired-value readings are explicitly out of scope for "Number" — a future dedicated type, not a stretch of this one. A tracker's type is locked at creation (same as templated trackers); only the name can be edited afterward, since changing type after data exists doesn't make sense. Custom trackers are reusable: creating one saves a persisted CustomTrackerDefinition, shown in a "Your trackers" section alongside official templates (search spans both), so next time it's a one-tap re-add rather than retyping from scratch — archiving/deleting the dashboard instance doesn't erase the underlying definition. Rename-cascade mechanism (renaming a definition updating all past/present instances) was deliberately not built — no rename UI exists yet to justify it, clean follow-up whenever one is built |
| Future use-case notes (not yet planned in detail, captured for later) | Broad usability without confusion is the stated north star. Real use cases named as examples, not an exhaustive list — many complex health conditions should be able to be handled here: bipolar disorder (symptoms, meds, therapies, sleep, treatments like ECT/peer support, regular clinical depression inventories with scores) and personality disorders similarly. Critical content principle: clinical terms must never be conflated with everyday emotional language — clinical depression is not "I'm sad/upset about X," and this needs to shape any future mood-related UI/copy. An "emotional health inventory" is a distinct future instrument idea, separate from clinical screening tools like PHQ-9/Goldberg. Chronic condition management (diabetes, multiple sclerosis) is a new template category, distinct from the existing acute-illness templates. Comorbidity view logic: some trackers (e.g. sleep) should reasonably surface under multiple concerns at once; medications should NOT automatically appear under every concern a profile has — meds specific to one condition (e.g. borderline personality disorder meds) shouldn't clutter an unrelated concern's view (e.g. diabetes), suggesting a "meds for other conditions" catch-all section. Note: medications currently have no concern-tagging at all in the built code — this idea requires that capability to exist first, which it doesn't yet |
| Template library will keep growing | Resolved architecture question: official templates keep expanding over time to cover more conditions, rather than custom-tracker-creation being the intended long-tail answer. Concrete implication: templates need a genuine `category` field as structured data, not the current ad hoc 3-category grouping (Common Illnesses/Mental Health/Aches & Pains) — that approach doesn't scale to dozens of conditions. Search stays the primary discovery method as the library grows, not browsing. This raises the priority (doesn't introduce new scope) of two already-open items: the medication concern-tagging gap, and the still-unresolved "who reviews clinical template content before shipping" open question — both become more pressing as clinically complex conditions (bipolar, personality disorders, MS, diabetes) get added, not just common illnesses |
| Template categories | Starting categories: "Mental Health & Illnesses" and "Physical Health & Illnesses." Category is a discovery aid, not a clinical classification — it never claims a condition is purely physical or purely mental. A template can belong to more than one category (many-to-many, same pattern as tracker-concern tagging), specifically because most complex conditions genuinely have both physical and mental symptoms (MS: mobility and fatigue alongside cognitive fog and mood) — forcing a single exclusive bucket would misrepresent the condition. The trackers inside a template span whatever mix of physical/mental symptoms is clinically relevant, independent of which category shelf it's browsable under |
| Doctor report — full-picture sections (future work, not built) | The report is currently scoped entirely to a 72-hour recent-activity window. Add two summary sections alongside that, not replacing it: a full history of every health concern ever created, including resolved and misdiagnosed ones, each shown with its full status history (see Concern lifecycle entry below), and a full list of every distinct medication ever logged as a summary (name/dose/first-last-logged), not a repeat of every individual dose — the detailed dose-by-dose ledger stays in the existing recent-window section |
| Health Connect/HealthKit — import direction (future, not built) | Extends the earlier-planned V2 sync work (originally scoped as symptom/temperature data written out) to also read in: step counts, sleep hours, blood glucose, and similar data that a device (CGM, wearable) may already write to Health Connect/HealthKit on its own. Same underlying platform, now bidirectional, not a separate integration. Resolved: imported entries carry a `source` field (manual vs. imported, and from where). Hard rule, not a preference: imports are additive-only — an import must never modify or replace an existing entry, even when it targets the same tracker/time as a manual one. On conflict, the manual entry stays untouched and the imported value surfaces separately for the user to review, never auto-merged or auto-replaced. Still open: read access is a bigger privacy step than anything built so far and needs the same explicit, never-silent consent treatment as everything else, if not more scrutiny; sleep apnea/CPAP data specifically is NOT assumed to fit the same pattern — that data often lives in manufacturer-specific platforms (e.g. ResMed) that may not route through Health Connect the same way steps/sleep/glucose do, and this needs verification before assuming it's covered by the general mechanism |
| Non-destructive design principle (implemented) | "Don't be destructive in ways that can't be undone" — resolved into concrete behavior for both items originally flagged. Deletion of entries/medications is soft-delete now, recoverable via a "Recently Deleted" panel, not immediate/permanent. Backup restore auto-downloads a snapshot of current data before overwriting, giving a real durable undo path. Kept as a standing lens for whatever gets built next, not considered "done" as a project-wide guarantee — just no longer an open gap for these two specific things |
| "Multiple Sclerosis" template (built) | Sourced from National MS Society, MS Society UK, NINDS, and a peer-reviewed symptom-frequency table — consistent across sources, logged to verified-facts-log.md. 14 trackers: Fatigue, Mobility/balance, Cognitive fog (core three, pre-selected first), Pain, Spasticity, Bladder, Bowel, Vision (boolean — often episodic, not a steady severity), Sleep quality, Falls (Number type — count per day), then Dizziness, Tremor, Speech, Swallowing difficulty as lower-priority options. Tagged under both Physical Health & Illnesses and Mental Health & Illnesses. Deliberately excluded: EDSS (clinician-administered only, not appropriate for self-report) and PHQ-9 (the questionnaire tracker type this would need still doesn't exist as a real feature — noted honestly as a gap, not silently dropped). Still open: the Number type's connected-line chart is an honest imperfect fit for falls specifically, since it can visually imply a smooth trend for what's really a discrete daily count |
| Template category system (built) | Added a `category` array field to every template (multi-category, not exclusive — a template can and does appear under more than one heading). Retroactively categorized the original 6 templates as "Common Illnesses." Browse view replaced its flat list with category-grouped headers (Common Illnesses / Physical Health & Illnesses / Mental Health & Illnesses), a template rendering under each category it belongs to, same multi-membership display pattern already used for tracker-concern grouping on the dashboard. "Aches & Pains" — also previously planned, also never built — intentionally left out of this pass, not forgotten |
| Flagged periods (implemented) | Generalized beyond MS-specific "relapse" per user's "etc" — a `flaggedPeriods` entity (label, start/end date, concernId) lets any period of time get labeled and shown as a shaded band on every chart for that concern's trackers. End date optional (ongoing if blank). Soft-delete/recoverable via Recently Deleted, same as entries and medications |
| Treatments (implemented) | New category for clinic-administered items (ECT, ketamine/chemo infusions, physical therapy) — same data shape as medications (name, detail, timestamp) but a genuinely separate list/section, since "something I take myself" and "something done to me at a clinic" are different enough conceptually to warrant separate logs, even though they're the same shape underneath. Chart architecture: rather than build a second parallel marker system, medications and treatments were merged into one shared "clinical events" timeline internally — same positioning, staggering, and per-name color hash — differentiated only by marker shape (diamond vs. circle). This keeps the chart code from duplicating, while still making the two types visually distinguishable. No free-tier cap applied to treatments (medications have a 15-name cap; treatments don't) — not requested, and adding one wasn't assumed by default |
| Questionnaire tracker type (implemented) | Generic score-based multi-question instrument mechanism, built without any real clinical content — PHQ-9 and GAD-7 remain unbuilt despite being licensing-cleared, and the Goldberg adaptation stays blocked. `licenseStatus` gate enforced in code, not just policy: `needs-review` items are filtered out of what's selectable. One deliberately original, clearly-labeled test placeholder included so the mechanism is demonstrable rather than invisible. Questionnaire entries can be deleted but not edited in place — the existing inline edit form doesn't support multi-question responses, scoped out as a separate task rather than built against no real content |
| Depression tracking for MS: plain 0-10 scale, not Goldberg or PHQ-9 (decided) | User's call, given Goldberg licensing remains unresolved: use a simple self-report 0-10 scale for now rather than wait, or build real PHQ-9 content despite it being available. Added directly to the MS template as a standard scale-type tracker, no new mechanism needed. PHQ-9/Goldberg via the questionnaire tracker type remain open future upgrades, not abandoned, just not the current path |
| "Aches & Pains" template (planned, not built) | New template category, friendlier naming than "musculoskeletal" per the project's plain-language standard. Parameterized by body part — first template where tracker names depend on a choice made at add-time: a quick-select (Neck/Shoulder/Back/Hip/Knee/Ankle/Wrist) plus free-text fallback, feeding into names like "Shoulder pain level," "Shoulder mobility," "Shoulder activity restrictions." One body part per add — multiple areas means adding the template again as a separate concern, not a multi-select in one pass. Trackers: pain level (scale), mobility (scale), activity restrictions (scale for now — a proper checklist/multi-select type is a bigger, separately-decided feature, not built into this template by default), did stretches/exercises (boolean). Medications need no new work — already work independently via concern-tagging. Template browse view needs real category headers now (Aches & Pains, Mental Health, Common Illnesses) rather than one flat list, given the picker has outgrown a single undifferentiated list |
| Concern lifecycle | Expanded from a binary active/resolved to four real statuses: **acute** (short-term, currently relevant), **chronic** (ongoing, not expected to "resolve" the way an acute illness does), **resolved**, **misdiagnosed** (the concern was tracked but the diagnosis turned out to be wrong — an honest correction, not a deletion). Status is user-set (not inferred) and changeable anytime, including moving back out of resolved/misdiagnosed if warranted — "reopening" is just changing status, no separate mechanism needed. A full `statusHistory` (status + timestamp per change) is kept per concern, not just the current status, specifically so the doctor report's full-history section can show the real timeline (e.g. acute → chronic → misdiagnosed), not just where things stand today. Resolving/misdiagnosing a concern does NOT touch its trackers' own archived state — independent, as before. Dashboard "By health concern" view: acute and chronic both stay in the active grouped view; resolved and misdiagnosed both move out of the day-to-day view (misdiagnosed doesn't belong in an active view, same as resolved) — but both remain fully visible in the doctor report's comprehensive concern history, which is the entire point of keeping the record |
| Multi-profile passcode model (planned, not built) | Shared household passcode unlocks the app and shows a profile switcher. Privacy is per-tracker, not per-profile or per-entry: any profile can set a personal passcode, and individual trackers (not entries) can be marked private, moving that tracker and everything logged under it into a separate encrypted partition keyed to the profile's own passcode — genuinely unreadable with just the shared passcode, not hidden by a UI switch. A concern can mix private and shared trackers; someone with only the shared passcode sees just the shared ones, fully silently — no indicator that private trackers exist, no count, nothing. The personal-passcode setting itself is the one exception to that silence: it's an ordinary, always-visible "Personal passcode: Not set / Set" row in profile settings, identical in spirit to any other toggle — visible that it exists, but revealing nothing about what's behind it. This also solves rememberability for free: no special indistinguishable-field mechanism needed, since seeing "Set" is enough to know to try entering it. Covers both named use cases: a parent tracking a child needs zero extra friction (nothing marked private, one shared unlock reaches everything); a teenager wanting real privacy marks specific trackers private under their own passcode. Direct consequence of doing this for real: a personal passcode inherits the same zero-knowledge/no-recovery tradeoff as the main app passcode — forgetting it makes everything marked private under it unrecoverable by anyone, independent of the rest of the profile's (and household's) data being fine. Must be disclosed plainly when someone sets one, not discovered later. Toggling a tracker's privacy after the fact is a real data-migration operation (moving it between encryption partitions), not just flipping a flag, though it should feel instant in the UI |

## Open questions (not yet decided)

- Passcode recovery policy: pure zero-knowledge (no recovery possible) vs. some form of user-held recovery code
- Report format: plain text (built) vs. PDF (originally specced for free tier) — which is the real target?
- Household/caregiver permissions: what exactly can a "caregiver" role do vs. "owner"?
- Illness template medical review process: who signs off on template content before shipping?
- Open-source PR review policy for security-sensitive code paths
- Cross-channel patch strategy (F-Droid review lag vs. instant web deploys)
- Support/refund/cancellation channel, given there's no account/login system
- Whether questionnaire-type trackers (PHQ-9, GAD-7, etc.) get any re-administration reminder, given they're meant to be retaken on a schedule (e.g. every 2-4 weeks) unlike ad-hoc symptom logging — if built, must be a passive in-app banner, never a push notification, per the no-notification-harassment rule

## Logging discipline (added after a gap where both logs fell behind)

Both `ai-usage-log.md` and `decisions-log.md` fell about 30 messages behind actual work during
one long build/debug session — the standing rule existed but wasn't being followed in practice
during rapid back-to-back edits. Fix going forward:

- **Log immediately, same turn, before presenting files** — not "I'll log this later," which is
  exactly what caused the gap. If a change is worth telling the user about, it's worth one line here.
- **Keep entries short** — a single row, not a paragraph. Low friction is what makes it sustainable
  across many small edits in a row, rather than something that only happens at natural checkpoints.
- **Bug fixes and root-cause diagnoses get logged too**, not just new features — several of the
  most important entries in this project (the Babel 8 issue, the service worker caching strategy)
  were debugging work, not feature work, and are exactly the kind of thing worth a durable record.
